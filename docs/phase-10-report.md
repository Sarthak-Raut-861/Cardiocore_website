### Detailed Explanation of Frame Accounting Discrepancy in Historical Run
- In the initial Phase 10 benchmark, the server generated and transmitted 1,475 frames, and the client received 1,475 frames with **zero sequence gaps**.
- The server sequence counter began at 1 and incremented consecutively to 1,475. Because all transmitted frames were delivered in FIFO order over the local WebSocket connection without packet drops, no sequence gaps were observed (`sequence_gaps = 0`).
- The 25-frame difference between the 1,475 received frames and the theoretical 1,500 frames ($300\text{ s} \times 5\text{ Hz}$) was **timing drift on the generator loop**, not dropped packets. Each generator iteration executed `asyncio.wait_for(..., timeout=0.20)`, after which async database session checks (~1–3 ms every 5 frames), waveform slicing, and packet packing added ~3.4 ms of scheduling overhead per frame ($203.4\text{ ms}$ average cycle). Over 300 seconds, exactly 1,475 cycles completed.
- **Drift Compensation Solution**: In the re-run test, the generator was updated to schedule ticks relative to stream start time (`target_tick = stream_start + seq * 0.20`). This compensated for loop processing time, delivering exactly **1,500 frames and 75,000 samples** over 300.04 seconds with **249.97 Hz achieved sample rate** (-0.01% deviation).

### 30-Minute Continuous Stream: Non-Execution Statement & Limitations
- **Status: NOT EXECUTED.**
- **Technical Rationale**: A 30-minute real-time stream requires transmitting 9,000 frames and 450,000 samples across 1,800 seconds. In interactive single-agent development environments and standard CI pipelines, running an unconditional 1,800-second blocking command exceeds practical execution turn limits and risks timeout aborts.
- **Evidence from 5-Minute Sustained Stream**:
  - Validated that client ring buffer occupancy remains strictly bounded at 1,250 samples ($< 50\text{ KiB}$) due to fixed slicing ceiling (`next.slice(-bufferCapacity)`).
  - Validated that WebSocket descriptors, session tracking, and async database connections do not leak over 1,500 consecutive frames.
- **Explicit Limitation**: A 5-minute test demonstrates short-term stability, sequence continuity, and bounded buffer behavior, but **does NOT prove multi-hour memory stability or production readiness under multi-tenant load**. Long-term soak testing remains deferred.

## 8. Batch Recovery, Database Uniqueness, and Idempotency Specification

### A. Precise Idempotency Key & Uniqueness Scope
- **Logical Uniqueness Key**: `(patient_id, lead_name, start_timestamp)`
- **Database Constraint**: `UniqueConstraint("patient_id", "lead_name", "start_timestamp", name="uq_telemetry_patient_lead_start")` on `telemetry_chunks`.
- **Single-Lead Enforcement**: All chunks in Phase 10 are strictly single-lead Lead-II (`lead_name = "Lead-II"`).
- **Scope Definition**:
  - `patient_id`: Scoped strictly per patient profile.
  - `lead_name`: Always `"Lead-II"` in Phase 10 scope.
  - `start_timestamp`: Microsecond-precision UTC start timestamp.
- **Classification Rules**:
  - **New Chunk**: No existing row matches key $\rightarrow$ Insert chunk into database, increment `processedChunks`.
  - **Identical Duplicate**: Existing row matches key AND stored `payload_checksum_sha256 == computed_sha` $\rightarrow$ Do not insert duplicate row, increment `duplicateChunks`.
  - **Conflicting Payload**: Existing row matches key AND stored `payload_checksum_sha256 != computed_sha` $\rightarrow$ Reject payload, do not overwrite existing data, increment `conflictChunks` and `errorCount`.
  - **Patient-Scoped Uniqueness**: Distinct patients submitting valid single-lead (Lead-II) chunks with identical timestamps have distinct composite keys (`patient_id`) and are both accepted and persisted without collision.

### B. Concurrency & Transaction Safety
- Under concurrent requests submitting identical batches simultaneously:
  - Database-level unique constraint prevents duplicate row insertion.
  - Application layer catches `IntegrityError` race conditions, performs session rollback, and re-queries the row to verify the checksum, ensuring all concurrent callers receive a successful HTTP 200 with accurate duplicate accounting.
- Under concurrent requests submitting conflicting payloads for the same timestamp:
  - The first committer succeeds; the concurrent conflicting submission is caught, rolled back, and classified as a conflict.

### Workload Duration Arithmetic Correction
- **Stored Sample Count per Chunk**: Exactly **50 samples** (each sample is an `int16` signed integer, 2 bytes; 100 bytes payload).
- **Sampling Rate**: 250 Hz single-lead ECG.
- **Represented Duration per Chunk**: $50\text{ samples} / 250\text{ samples/sec} = 0.200\text{ seconds}$ (200 milliseconds).
- **1,000 Chunks Workload**:
  $$\text{Total Samples} = 1,000 \times 50 = 50,000\text{ samples}$$
  $$\text{Total Represented ECG Duration} = \frac{50,000}{250} = 200.0\text{ seconds} = 3\text{ minutes } 20\text{ seconds} = \mathbf{3.33\text{ minutes}}$$
- **Correction of Draft Report Inconsistency**:
  The draft report stated that 1,000 chunks represented "~3.3 hours". This was a units transcription error: $200\text{ s} / 60\text{ s} = 3.33\text{ minutes}$, which was transcribed as hours (a $60\times$ transposition). Storing 3.33 hours (12,000 s) at 250 Hz would require 3,000,000 samples (60,000 chunks of 50 samples each, or 1,000 chunks of 3,000 samples / 12 seconds each).
